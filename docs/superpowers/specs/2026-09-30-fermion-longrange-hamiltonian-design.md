# fermion モードの長距離ハミルトニアン(次近接以上のボンド)— 設計書

2026-09-30、ブランチ `fermion-longrange-ham`(develop b32a8dba から)。

## 1. 目的と範囲

fermion モードで、最近接より遠いボンドを含むハミルトニアンの基底状態を計算できるようにする。
対象とする模型は次のとおり。

- 正方格子の t-t'-t''(Hubbard / スピンレス)と、次近接の密度相互作用 V'
- 三角格子の Hubbard / スピンレス(正方格子表現では NN の一方向が反対角の 2 ホップになる)
- ハニカム格子とカゴメ格子の Hubbard / スピンレス(NN と、それより遠い項)

**やること**

- 虚時間発展ゲート:長距離ボンドのゲートを、最短経路に沿った NN ゲート列(graded MPO)に分解する。分解はツール(`tenes_std`)で行い、シンプル更新(SU)で適用する。
- solver 側:物理次元が一時的に変わるゲート列を、パリティ台帳を持ち回して受け付ける。
- `tenes_simple`:正方格子の 2・3 近接項と、三角・ハニカム・カゴメ格子を fermion で許す。
- D = 1 の仮想脚と物理次元 1 のサイト(空孔)を含む単位胞で、既存の fermion 経路が正しいことを検証し、必要なら直す(フェーズ 2)。

**やらないこと**

- フル更新(FU)での長距離ゲート。入力時に拒否する(§6.1)。
  FU では、ゲート列の途中で物理脚が太ったテンソルから CTM 環境を作ることになり、その環境の妥当性がボゾンでも検証されていないため。別件とする。
- 測定窓(4×4、|dx| ≤ 3 かつ |dy| ≤ 3)の外に出るハミルトニアンボンド。エネルギーを測れないので、従来どおり拒否する。
- 有限温度・実時間発展(fermion モード全体で未対応のまま)。

## 2. 現状

- ボゾンの長距離ボンドは、`tenes_std` の `make_evolution_twosite`(`tool/tenes_std.py`)が `LatticeGraph.make_path()` の経路に沿って逐次 SVD で NN ゲート列に分解する。
  経路は、D = 1 のボンドを通らない重み付き最短経路である(重みは 1/D² に位置のタイブレークを足したもの。単位胞をまたぐ辺は重み 2 倍)。
  そのため、ホップ数が Manhattan 距離より多い経路になることがある。
- ゲート列の途中サイト m では、物理脚が MPO ボンド χ に置き換わる(物理次元が一時的に変わる)。次のゲートが χ を消費して、元の次元に戻す。脚の並び(TeNeS の二サイト演算子の配列規約 `op[in1, in2, out1, out2]`)は次のとおり。
  - 先頭ゲート:`(in_s, in_m1, out_s, χ1)`
  - 中間ゲート:`(χ_{k}, in_{m_{k+1}}, out_{m_k}, χ_{k+1})`
  - 末尾ゲート:`(χ_last, in_t, out_{m_last}, out_t)`
- fermion モードでは長距離ボンドを次の箇所で拒否している。
  - `tenes_std`:`_validate_fermion_mode_input`(`nhops != 1` を拒否)
  - solver:`validate_fermion_constraints`(`src/iTPS/load_toml.cpp`)。二サイトゲートのパリティ検査が、両サイトの物理台帳(固定)を前提にしている。
  - `tenes_simple`:`_check_fermion_scope`。正方格子以外と、2・3 近接の項を拒否する。
- fermion の SU(`src/iTPS/simple_update.cpp`)は、ゲートを `wrap_twosite_gate(op, p1, p2)`(`src/fermion/fops.hpp`)で包む。入力と出力に同じ台帳 `{p1, p2, p1, p2}` を付ける。
  source が raster で後ろ側(`source_leg` が 0 か 1)のときは、graded transpose `Axes(1, 0, 3, 2)` でサイトの役割を入れ替える。
- 長距離の二サイト測定(PR #117)は 4×4 窓の中ですでに動く。演算子の定義は、source 先の順序付き Fock 基底である(PR #117 設計書 §4.2)。
- `tenes_simple` の `SpinlessFermionModel` と `HubbardModel` は、`t'`・`t''`・`v'` などのキーをすでに解釈する。拒否しているのは `_check_fermion_scope` だけである。
  カゴメの空孔に `parity = [0]` を出力する処理も、すでにある。

## 3. 演算子の定義

std.toml の長距離ボンド (s, dx, dy) の行列 `evo[i_s, i_t, o_s, o_t]` は、source 先の順序付き Fock 基底
|n_s n_t⟩ = (c†_s)^{n_s} (c†_t)^{n_t} |0⟩ での行列要素とする。最近接ボンドや長距離測定の定義と同じである。
SU が最小化する H と、測定が評価する H は、同じ演算子でなければならない。

## 4. 方式:経路順の graded MPO

### 4.1 考え方

ゲート列の各 NN ゲートは、χ 脚を含めてパリティ偶とする。途中サイト m の太った物理脚 χ は、「サイト m の一時的な局所空間」(graded、次元 χ)とみなす。
すると各ゲートは局所空間の間の偶写像になり、偶写像の合成はグローバルなモード順に依存しない。
そこで、raster 順ではなく**経路順 (s, m1, …, m_k, t)** を抽象的なモード順として採り、この順で O_st ⊗ 1_mid を素の行列に書く。

O_st = Σ_c Â_c B̂_c(チャネル c のパリティ p_c)を経路順の基底に作用させると、B̂_c が途中サイトの生成演算子を越えるたびに (−1)^{p_c · p(x_m)} が出る。
よって、経路順の多サイト行列は次のとおりである(TeNeS の配列規約で、入力脚を先、出力脚を後に並べる)。

    T[i_s, i_m1, …, i_mk, i_t ; o_s, o_m1, …, o_mk, o_t]
      = evo[i_s, i_t, o_s, o_t] · Π_m δ(i_m, o_m) · (−1)^{(Σ_m p(i_m)) · (p(i_t) + p(o_t))}

(p(i_t) + p(o_t) はチャネルのパリティ p_c に等しい。evo が偶なので、非零要素ではこの値が一つに決まる。)

これを、ボゾンと同じ脚の並びで逐次 SVD する。ただし、各段の SVD は**パリティブロックごと**に行う。
T が偶なので、各段で行列化した C[(行), (列)] は行添字のパリティでブロック対角になる。ブロックごとの SVD により、χ の各添字のパリティが確定する。

solver の NN 向き正規化(raster 化の graded transpose)は、偶ゲートであれば入出力の次元が違っても成り立つ。そのため solver 側に新しい符号は入らない。
**この主張が本設計の要であり、T2 のゲート(§4.3)で反証を試みる。**

### 4.2 1 ホップとボゾン

1 ホップ(NN)のゲートと、ボゾンの分解経路は変えない。

### 4.3 前提の検証と中止条件(T2 のゲート)

C++ の SU のボンド処理を、ゲート列の順に打ち切りなしで当てる。その物理状態が、Fock oracle(`test/fermion/fock_oracle.py`。物理モードは raster 順)で O_st を直接当てた物理状態と、全体のスカラー倍を除いて一致することを確かめる。
経路は少なくとも次を含める。

- (dx, dy) = (2, 0)、(0, 2)、(−2, 0)、(0, −2):直線の 2 ホップ。source が raster で後ろ側になる向きを含む。
- (1, 1)、(1, −1)、(−1, 1)、(−1, −1):対角と反対角。曲がり角の 4 方向。
- (2, 1)、(−2, 1):3 ホップで曲がり角を含むもの。
- 奇チャネルを必ず含む演算子(c†_s c_t + h.c.、Hubbard の両スピン)と、偶チャネルだけの演算子(n_s n_t)。

一つでも合わなければ(「特定の向きだけ符号反転」も含む)、§4.1 の議論が誤りである。その場合は実装を曲げずに作業を止め、設計に戻る。
PR #117 で「ボンドの向きの符号」を設計書が落としていた前例があるので、曲がり角の 4 方向と、source が後ろ側になる向きは省略しない。

## 5. ツール

### 5.1 `tenes_std`

- `_validate_fermion_mode_input` の `nhops != 1` の拒否を外す。自己隣接セルの拒否と、パリティ台帳の必須化は残す。
- `make_evolution_twosite` に fermion 用の分岐を足す(fermion モードで、かつ 2 ホップ以上のとき)。
  - §4.1 の T を作る。途中サイトの物理パリティは、`tensor.unitcell` の `parity` から取る。
  - 逐次 SVD はパリティブロックごとに行う。各ブロックで、特異値 ≤ ε·s_max(ε は実装で決める。1e-14 程度)を落とす。
    全要素がゼロの χ 添字を出さないためであり、solver の推定(§6.1)の前提になる。
  - 出力の形式(`[[evolution.simple]]` の `source_site`・`source_leg`・`dimensions`・`elements`)は変えない。**χ のパリティ表は書かない。**
- fermion モードで長距離ボンドがあり、`parameter.full_update.num_step > 0` の場合はエラーにする(§1)。これは利用者に早く知らせるための補助で、規範となる拒否は solver 側(§6.1)が次元と台帳で行う。
- 測定窓の外のボンドは、solver の既存ガードで拒否される。`tenes_std` でも同じ理由で先に拒否してよい(実装で判断する)。

### 5.2 `tenes_simple`

- `_check_fermion_scope` の拒否を次のように緩める。
  - 格子:正方・三角・ハニカム・カゴメを許す(フェーズ 1 では正方・三角、フェーズ 2 でハニカム・カゴメ)。
  - 2・3 近接の項を許す。
  - `[correlation_length]` の拒否は残す。
- docstring(「nearest neighbour only」「square lattice」)を更新する。
- 既存テスト(`test/python/test_tenes_simple.py` など)の、これらを拒否することを確かめているケースは、テスト作成者が更新する。

## 6. solver

### 6.1 入力時の検証(`load_toml.cpp`)

現行の「奇の二サイトゲート」ガード(`evolution.simple` と `evolution.full` の二サイトゲートを、固定の物理台帳で検査するもの)を、**ゲート列の模擬実行**に置き換える。

模擬実行は、**実際に実行されるゲートのリストと順序**に対して行う。`evolution.simple` では、`complete_ungated_bonds()`(`src/iTPS/load_toml.cpp`)が未ゲートの NN ボンドに identity ゲートを足した後のリストである(現状でも `main.cpp` はこの順で呼んでいる。これを要件として固定する)。
identity ゲートは元の `lattice.physical_dims` で作られ、リストの末尾に足される。そのため、ゲート列が閉じた後に来る。
順序が変わって、太った脚に identity ゲートが当たるような入力があれば、模擬実行の次元検査で拒否される。

`evolution.simple` と `evolution.full` のそれぞれについて、群ごとに次を行う。

1. 各サイトの「現在の物理台帳」を `tensor.unitcell.parity` で初期化する。
2. ゲートを入力順にたどる。各二サイトゲート `op[in1, in2, out1, out2]`(1 = source、2 = target)について:
   - `in1`・`in2` の次元が、source・target の現在の台帳の長さと一致すること。台帳はそのまま入力脚の台帳にする。
   - `out1` は source の**元の**物理台帳とする。次元が元の物理次元と一致しなければ拒否する。
   - `out2` の台帳は推定する。非零要素ごとに p(out2) = p(in1) + p(in2) + p(out1) mod 2 を求める。
     同じ添字で値が食い違えば(混在)拒否する。非零要素を一つも持たない添字があっても拒否する。
     推定で決めるので、ゲートは構成上つねに偶になる。
   - source の現在の台帳を `out1` の台帳(元の台帳)に、target の現在の台帳を `out2` の台帳に更新する。
   - 一サイトゲートは、入出力の次元が現在の台帳と一致し、偶であることを確かめる(台帳は変えない)。
3. 群の終わりに、全サイトが元の物理次元と元の台帳に戻っていることを確かめる。
   NN の奇ゲート(例:c_t を含むもの)は、2 の推定で target の台帳が反転した状態になり、ここで拒否される。従来の「奇の二サイトゲート」ガードの役割は、この検査が引き継ぐ。

**ゲート列の規約**(入力形式の意味として docs に明記する):物理次元が変わるゲートでは、太る脚は target 側の出力 `out2`、消費される脚は source 側の入力 `in1` である。
`tenes_std` の分解は経路の手前側を source にするので、この規約に従う。out2 を推定で決め、`out1` を元の台帳に固定するのはこのためである。
「出力の次元が元と同じなら元の台帳」という規則にすると、χ の次元が偶然 d と等しいとき(Hubbard で χ = 4 など)に、正しいゲートを誤って拒否する。

推定した 4 脚の台帳は、ゲートごとに保持する(例:`EvolutionOperator` にパリティ台帳の欄を足す。ボゾンでは空)。実行時に再推定はしない。

**FU の拒否(規範となる規則)**:`evolution.full` に「`out2` の台帳が target の元の台帳と異なる」ゲート、または「入力脚の次元がそのサイトの元の物理次元と異なる」ゲートがあり、かつ FU の `num_step` のどれかが正なら拒否する。
C++ は分解後のゲートの出自(長距離ボンドかどうか)を知り得ない。そのため、判定は次元と台帳で行う。
FU の実行時(`src/iTPS/full_update.cpp`)は、固定の `finfo.phys` でゲートを包んだままにする。`tenes_std` 側の拒否(§5.1)は、利用者に早く知らせるための補助である。

**MPI**:テンソルは分散しているので、推定と検査は全ランクで集団的に行う(非零要素の有無を添字ごとに集約する)。
拒否は全ランクで同じ判定になり、全ランクが投げること。rank 0 だけが投げるとハングする(過去の再発パターン)。

拒否メッセージは既存の `throw_fermion_guard` の形式に合わせ、ゲートを特定できる情報(群、入力中の順番、source_site、source_leg)を含める。

### 6.2 実行時(`simple_update.cpp`)

- 入出力で別々の台帳を受け取る `wrap_twosite_gate` の版を足す(4 本の台帳を取る)。既存の 2 本版は、それに同じ台帳を 2 回渡す薄い包みにしてよい。
  入力脚の swap(`apply_swap(fop, 0, 1)`)の規約は変えない。
- fermion の二サイトゲートを当てるとき、§6.1 で保持した台帳でゲートを包む。raster 化の graded transpose は、4 本の台帳ごと入れ替える。
- 適用後、物理台帳を更新する。**更新は raster 化(graded transpose)の後の、正規化されたサイト s1・s2 と、変換後のゲートの出力脚の台帳で行う。** TOML 上の source・target と `out1`・`out2` で行ってはならない。
  経路が左か上に進む段(TOML の `source_leg` が 0 か 1)では、太る脚は TOML では `out2` だが、変換後は s1 側の出力脚になる。
  これで、ゲート列の途中では m の台帳が χ になり、末尾ゲートで元に戻る。
- 群のスイープの後、物理台帳が元どおりであることを内部不変条件として確かめる(入力検証で保証されているので、違反は論理エラー)。
- `log_fermion_sector_dimensions` など、SU の途中で `finfo.phys` を読む処理が、太った台帳で壊れないことを確かめる。
  測定・保存・CTM 更新は SU の群ループが閉じた後にしか走らないことも、実装時にコードで確認する。

## 7. フェーズ 2:D = 1 の脚と空孔(ハニカム・カゴメ)

### 7.1 背景

- ハニカムは、幅を倍にした正方格子に埋め込まれる。各サイトの仮想脚のうち 1 本が D = 1 である。skew も使う。NN はすべて 1 ホップで、NNN は D > 1 のボンドに沿った 2 ホップになる。
- カゴメは、2×2 に倍化した 4 サイトのうち 1 つが空孔である。空孔は物理次元 1、仮想脚はすべて D = 1 である。**NN の時点で 2 ホップのボンドを含む**(例:B → C の (−1, 1) は A を経由する)。そのため、フェーズ 1 のゲート列に依存する。
- これまでの fermion の検証は、すべて D > 1 の正方格子で行ってきた。D = 1 の仮想脚と物理次元 1 のサイトを含む単位胞は、どの fermion 経路でも検証されていない。

### 7.2 T4 のゲート

D = 1 の脚と空孔を含む開放パッチで、既存の fermion 経路を Fock oracle と照合する。

- SU のボンド処理(隣に D = 1 の脚を持つサイト)
- CTM と MF の NN 測定
- 長距離測定のリレーが D = 1 のボンドや空孔を横切る場合。κ を次元 1 のボンドに融合すると台帳が [odd] になる。原理上は正しいはずだが、確かめる。
- 相関関数の鎖が D = 1 の脚を通る場合
- 保存と読み込み(D = 1 の脚の台帳)

不具合が見つかれば、このフェーズ内で直す。直し方が大きい場合は、統括が設計に戻して判断する。

## 8. テスト方針

- **T1(Python)**:`tenes_std` の fermion 分解を、経路順の Fock 空間で合成して O_st ⊗ 1_mid と機械精度で比べる。χ の各添字のパリティが一つに決まることも確かめる。
  経路は §4.3 の一覧に合わせる。ボゾンの分解が変わらないこと(既存の出力とバイト一致)も確かめる。
- **T2(C++、§4.3 のゲート)**:SU のボンド処理を打ち切りなしで当てた結果を oracle と比べる。拒否系の単体テストも作る:χ 添字の混在・全ゼロの添字・群の終わりで元に戻らない・次元の不一致・FU での長距離ゲート。
  打ち切りなしにするには、ボンドの仮想次元を演算子のランクより大きくとる必要がある。
- **T3(E2E)**:スピンレス t-t' 自由フェルミオンのエネルギーを、厳密値と比べる。厳密値は k 積分で求める(ε(k) = −2t(cos kx + cos ky) − 4t' cos kx cos ky)。
  t' の符号を反転させたときのずれが、D の打ち切り誤差より十分大きい点を、T3 の冒頭で実測して選ぶ。三角格子 Hubbard は golden で比べる。
- **T5(E2E)**:ハニカム(グラフェンのバンド)とカゴメ(平坦バンドを含む 3 バンド)の自由フェルミオンを、厳密値と比べる。ハニカムの NNN を含むケースも入れる。Hubbard は golden で比べる。
- **変異テスト**:少なくとも次がテストで検出されることを確かめる。
  - P の紐を外す(§4.1 の符号因子を消す)
  - ブロック SVD を素の SVD に替える
  - SU で `finfo.phys` の更新を止める
  - raster 化の graded transpose で、入出力の台帳を入れ替え忘れる
  - 物理台帳の更新を、raster 化の前の TOML 上の source・target と `out1`・`out2` で行う。
    右と下にしか進まない経路では、この変異は生き残る。そのため、経路が左か上に進む段(`source_leg` が 0 と 1 の両方)を含むゲート列で検出されることを確かめる。

- **既存テストの更新**:今回許可するものの拒否を確かめている既存テストは、テスト作成者が更新する(実装担当は触らない)。
  少なくとも次がある。`test/python/test_fermion_models.py` の格子の拒否(三角・ハニカム・カゴメ)と 2・3 近接の項の拒否、`test/python/test_tenes_std.py` の長距離ボンドの拒否。
  C++ の「奇の二サイトゲート」の拒否(`test/fermion/fermion_guards.cpp` など)は、§6.1 の群末検査で引き続き拒否されることを確かめる形に保つ。
  フェーズ 1 の時点では、ハニカムとカゴメの拒否テストは残す(T5 で更新する)。

ctest は `OMP_NUM_THREADS=1` で回す。MPI ビルド(n = 1, 2)でも回す。

## 10. リスク

- **§4.1 の議論の誤り**:T2 のゲートで止める。
- **SU のコスト**:Hubbard(d = 4)の 2 ホップでは、χ が最大 d³ = 64 になる。途中サイトの物理次元が 16 倍になり、SU のボンド処理の QR と SVD が重くなる。T3 で実測し、問題なら χ の打ち切りを検討する(本設計では行わない)。
- **経路がホップ数最小でない**:重み付き最短経路なので、Manhattan 距離より長い経路になることがある。§4.1 は任意の経路で成り立つので正しさには影響しないが、コストが増える。
- **D = 1 の脚まわりの未知の不具合**:T4 で洗い出す。規模が大きければフェーズ 2 を別ブランチに切り出す。
